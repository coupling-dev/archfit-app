Earlier explorations

Superseded by Archfit Guardrails, which is built on the product's real job: the loop between coding agents and the gate, and the decisions only owners can make. These three directions explored how to display the architecture. They stay here for comparison. Archfit keeps a repository's architecture from eroding: owners define layers, module contracts, and rules, and every pull request is checked against them. These prototypes show three ways to present that to people who think in modules and coupling. Same data, same jobs, different primary surface.

A

Atlas

map-first

The living architecture map is home. Layers are bands, links show what the code does, and colors show where it breaks the intent.

  • Click a module or a link to inspect it
  • PR lens overlays a change on the map
  • Policy changes start from the map

Charter

policy-first

The intended architecture as a readable charter that owners agree on. Rules read as sentences, and each shows whether the code complies.

  • Module contracts, rules, exceptions, debt
  • A dependency matrix scales past 50 modules
  • Changes are amendments made through a PR

Radar

change-first

Architecture erodes one pull request at a time. Home is the stream of open changes and the decisions owners must make.

  • Inbox of PRs with their architectural impact
  • Decision queue for policy owners

Where this led

The approved policy is the product's core contract, so a repository's home is the charter: layers, module contracts, rules with compliance, exceptions, and debt. Show the same model two ways: the Atlas map for small repositories and for explaining, the Charter matrix past about 20 modules. Give policy owners Radar's decision queue as their entry point, and use Radar's compact comment on GitHub. Leave trends out until the product decides to store per-run summaries.

Guardrails keeps this: its Architecture tab switches between charter text, map, matrix, and YAML.

How to read a prototype
  1. Start on the first tab. It is the direction's home.
  2. The sidebar on each view explains what you can do there, why it looks that way, and which data it needs.
  3. Open Design notes in the header for the full case: who it suits, costs, and risks.
  4. Switch Light and Dark in the header. Both are designed.
Six jobs in every prototype
  • Repositories and status
  • The architecture map
  • Module and seam detail
  • Change the policy through a draft PR
  • The PR on GitHub: two checks and one comment
  • Waivers and debt
Rules every prototype keeps
  • Reports are customer-attested, never "verified"
  • The gate is success, failure, or action required
  • No publish button. Every change is a PR merged on GitHub
  • Owner approval is for the exact commit
  • AI proposals never change the gate
  • No single health score
