## 1. Verdict

1. **Slow is server-side, and it is one thing: serial GitHub calls at about 240–330 ms each.** Client work is cheap (no long tasks, every interaction under 135 ms). pumba Home takes 12 s for a 2 KB answer.
2. **The Diagram is unusable above about 10 modules.** ccgram draws a 5884×4960 SVG shrunk to 20 %: module names 3.5 px high. There are no controls at all.
3. **Home does not answer "what state is this and what do I do".** The primary button is always `Continue setup`, which is an anchor to the same page, even when setup is complete or when a workflow change waits for the owner.
4. **Three dead ends**: Policy on a repository without a policy, every stale owner link, every unknown page.
5. **Colours match Primer; components do not match each other.** Six status looks, seven disclosure looks, four page-title shapes, underlined buttons, a black primary button on one page.
6. **The wording contract of the design is met by exemption, not by wording.** Over 20 phrases are whitelisted in the specs; `Needs attention`, bare `gate`, `Signed`, `review` are on screen.
7. **Copy is defensive.** `Not provided`, `Not checked here`, `Not recorded`, `payload`, `this response`, `as reported by the server` tell the user what the App does not know instead of what is true.

### 4.1 Home → The map → Diagram

| Repository | Modules / lines | Native SVG | Scale on screen | Module name height | Line label height |
|---|---|---|---|---|---|
| ccgram | 24 / 106 | 5884×4960 | 0.20 | 3.5 px | 3 px |

Causes, in code:
- Every line gets its own lane: 24 px of width and 30 px of height per line (`web/src/components/map/layout.ts:73-77`, `:102`). Size grows with the number of lines, not modules.
- The SVG is `max-width: 100%; height: auto` (`Diagram.svelte:75`): it shrinks to the column and the page grows to 1835 px. No scroll box, no minimum scale.
- 86–106 permanent labels that all say "Allowed dependency" or "Exception", with no endpoints.
- No pointer, wheel or key handler; not focusable; no `<title>` on modules or lines. Wheel scrolls the page, drag selects text.
- The legend sits below the chart, up to 1835 px from its top.
- Dash styles for the five kinds cannot be told apart at 20–30 % scale; drift differs from allowed by colour only.

### 4.2 Policy → Show graph

- Fixed 480 px wide in a 1198 px column, inside a 420 px scroll box (archfit content 1064 px).
- Names cut at 17 characters: 8 of 17 on archfit, 5 of 24 on ccgram.
- 78–104 unlabelled curves that pass through modules.
- Four colours for six layers: `cmd` = `support`, `adapter` = `model` (`PolicyGraph.svelte:28`).
- Clicking a module scrolls the page about 1100 px up to its table row; the graph is left off screen.

### 4.3 The two graphs differ in everything

Layer bands vs colour-coded modules; orthogonal vs curved lines; five line styles vs one; "An allowed dependency" vs "→ Allowed dependency" vs the Matrix's "Explicit allow"; volatility shown vs layer shown; arrowhead geometry. Only the Policy graph says "Allowed dependencies, not observed imports."

### 4.4 Proposed design (fits the CSP and the size budget; about 1–2 KB hand-written, no library)

CSP is `script-src 'self'`, no `unsafe-eval`, no inline `style=` attributes; the only runtime dependency is elkjs in a worker. So: no chart library, drive the SVG `viewBox` from state.

1. **Viewport**: fixed height `min(70vh, 720px)`, `overflow: hidden`, `touch-action: none`. The page stops growing.
2. **Start readable**: fit to width, but never below about 11 px label height. If that does not fit, start at the floor, top-left, and let the user pan.
3. **Move and zoom**: drag to pan; Ctrl/⌘ + wheel and pinch to zoom at the pointer (plain wheel keeps scrolling the page); double-click zooms in.
4. **Toolbar** of real buttons: `+`, `−`, `Fit`, `100%`, `Full screen`. Keyboard: arrows pan, `+`/`−` zoom, `0` fit, `Esc` leaves full screen.
5. **Focus**: click or focus a module → its incoming and outgoing lines stay, the rest dims; line labels show only for the selection, with both ends named ("handlers → api · exception until 2027-01-15"). Click again or `Esc` clears.
6. **Find a module**: an input with a list of module names; choosing one pans to it and focuses it.
7. **Legend at the top**, same words as the Matrix legend and the design's 12.2 list. One caption: "An arrow points at the module it depends on. Outer layer on top. Allowed dependencies, not observed imports."
8. **Routing**: replace the lane-per-line bus. Either ELK `layered` with orthogonal routing (elkjs is already in the worker), or draw only the selected module's lines plus one thin line per layer pair. Use `vector-effect: non-scaling-stroke`.
9. **One component** for the Home Diagram, the Request map and the Policy graph: same module box, same layer bands, same legend, more than four layer colours or none.
10. Optional later: minimap, collapse a layer, download SVG.

### 4.5 Matrix

- 24 columns need 2744 px; only about 8 are visible. Make a compact density the default from about 12 modules: vertical or 45° column headers, 32 px symbol-only cells, row header about 220 px. 24 columns then fit in about 990 px.
- Break names only at `_` and `-`, never mid-word; full name in `title`.
- Exception details must show the date and days left, or the legend must stop promising them ("Exception (expiry in details)").
- On ccgram nearly every `✓` carries `◷`. Mark only exceptions near their date strongly; show a count for several.
- Shade the diagonal; make blank cells quiet for screen readers (289 identical "deny status not fully evaluated" labels on archfit).
- Show the filters from about 12 modules, not 50.
- A one-module repository draws a 1×1 empty grid: say "One module is declared, so there is nothing to draw."
- The scroll box is nested in a long page and its horizontal scrollbar is at the bottom of the box: add a visible hint or the compact density above.

## 5. Page by page

Each block: what the page is for · what the user must understand · what is wrong · proposed copy. Proposed copy avoids the design's Not-used words (see section 8).

### 5.1 Repositories `/`

For: pick a repository, see which one needs setup. Must understand: which repositories work, which need something.

- The `Needs attention` column says `Not checked here` on all five rows, and a note repeats it. Remove the column and the sentence. (`Needs attention` is also a Not-used phrase.)
- `Required check: Check` — "Check" is the status value, the noun, and a button elsewhere. The footnote explains the word instead of fixing it. Proposed values: `required` / `not required` / `not confirmed`, footnote: "Not confirmed: the App cannot read this repository's rulesets. Ask a repository administrator."
- Two links per row go to the same page (name and `Open Home`). Keep the name; show `Continue setup` only when setup is incomplete.
- The list and Home disagree on what "required" means: pumba shows `Required` here while Home step 4 is `Action needed` (the check is required, pull requests are not). archfit shows `Check` here while Home shows both rules as `Action needed`. Cause of the archfit case not verified.
- The design's M3 asks this page for the repository state (`clean`, `drift`, `expired`, changed outside the flow, not set up). The page shows setup stages instead.
- Intro "Required check is separate from policy approval." assumes both ideas are known. Proposed: "Policy approved: an owner approved the policy. Check required: GitHub does not merge until `archfit/gate` passes. They are set separately."

### 5.2 Home `/r/<owner>/<repo>`

For: the state of one repository, what waits for the owner, the map. Must understand in five seconds: is it working, is anything waiting for me, what is the one next step.

| Repository | Status line as shown | Primary button | Real next step |
|---|---|---|---|
| archfit | `drift` | `Continue setup` | open the drift issue; turn on the two rules |
| archfit-4-mechanics | `clean` | `Continue setup` | none |
| ccgram | `the check could not read every place` | `Continue setup` | none in setup; the status is unexplained |
| pumba | `1 workflow change waits` | `Continue setup` | `Review workflow change · PR #417` (2000 px down) |
| coupling-dev/archfit-app | `Set up this repository.` | `Continue setup` | add the policy |

- `Continue setup` is `href="#setup-title"`; setup is already at the top. Replace with the step's own action, or with the owner item when one exists, or nothing.
- At 4 of 4 the whole setup box (about 1300 px, four ruleset rows) stays above the map, with the line "Policy approval and required-check settings are separate. Complete the applicable steps below." under "Setup is complete." Collapse to one line: "Setup complete · check required".
- `Needs you` sits below setup; items are bare links with no kind, no age. Move it directly under the page head; mark links that leave for GitHub.
- All five status lines use the same grey dot. `drift` and `clean` are the design's state names and stay lowercase; give them a tone and one sentence: "`drift` — the default branch has dependencies the policy does not allow. Issue #210."
- "the check could not read every place": "place" is undefined. Proposed: "The last check could not read every file, so the state is not known."
- Step 4 title `Require the gate`: the design does not use bare "gate". Proposed: "4 · Require the `archfit/gate` check".
- Step 3 says the owner "signs" the policy and the chip can read `Signed`. The design says there is no signature in 4.0. Proposed: "The owner approves the policy with a passkey. The approval covers these exact files; any later edit needs a new approval."
- Step 3 reads as actionable while step 2 is not done ("Review the proposed files before approving." with no files). Proposed chip: `after step 2`.
- Step 1 for a new repository: "The default branch has no version 3 policy." / `archfit init` / "…adds its agent block to AGENTS.md. It does not write the workflow." A newcomer does not know where to run it or where the workflow comes from. Say both, with a link.
- Ruleset rows repeat the same instruction paragraph and the same two links; the same GitHub page is linked seven or more times. State the three shared steps once; rows say only what to tick.
- The administrator-bypass row is three paragraphs about what the App cannot read. Fold it: "Optional. Keep an emergency bypass for administrators only. The App cannot read bypass lists; check Settings → Rules → Bypass list."
- The policy-push row on a personal repository is a paragraph that ends "there is nothing to do". Hide it when it does not apply.
- Chips: six values in two vocabularies (`Done` / `Action needed`; `On` / `Advisory` / `Verify yourself` / `Does not apply`), set in bold monospace, and `Advisory` is amber like `Action needed`. `Advisory` is also the name of a check mode in the policy.
- Headings are inverted: H1 24 px, section H2 14 px, step H3 15 px. H1 `Home` repeats the active tab; the repository name appears in the breadcrumb and again under the H1.
- `View policy` appears three times (page head, step 1 as "View the policy", step 2) plus the tab.
- On coupling-dev/archfit-app `View policy` leads to "Page not available".
- Matrix copy: "Blank = no explicit relationship in this payload, not "no imports" or "permitted". Deny status is only known for touched, requested or drift pairs; full deny evaluation is not available." Proposed: "Blank: the policy says nothing about this pair. It does not mean the dependency is allowed." Move the deny caveat into one closed "About this view".
- Details dialog: "All payload statuses", "Evidence scope", "No observed dependency counts, scan coverage or snapshot identity are provided." Proposed heading "About this pair"; drop the sentence ("scan" is a Not-used word and the matcher cannot see inside a closed dialog).

### 5.3 Policy `/r/<owner>/<repo>/policy`

For: read the approved rules; owners edit. Must understand: who owns it, what is enforced, what is excepted and until when.

- No policy yet → generic "Page not available" with no tabs. Proposed empty state: "No policy on the default branch yet. Open Home to continue setup."
- `Check mode · configured: advisory` beside `34 Blocking rules` (archfit) contradict each other. "Check mode" is an invented label for the `gate` key. Proposed: "The check: advisory — it reports and does not stop a merge" / "required — a failing rule stops the merge", and the count as "34 ask and deny rules".
- `Not provided` for Approval, exception Owner, Expiry, Request, Instead, Layers. On ccgram all 130 exceptions show three `Not provided` cells; the page is 15,228 px with every row in the DOM. Hide columns that are empty for every row, group by rule ("coupling · 62"), show 20 at a time, and say once "130 exceptions have no end date."
- "Live enforcement and approval evidence are not provided by this response." Proposed: link to Home, where that state is shown.
- `Not checked` chip on notes is the design's word and stays; explain it once at the top of Rules: "A note is not checked. It tells the reader what to do."
- Rule names here ("Module dependencies", "Coupling") differ from the ids on Pull and Request (`graph`, `coupling`). Show the id as the name.
- `Digest: sha256:…` with `Copy digest` on the main view; the design shows digests only on demand; the user guide calls it "fingerprint". Fold it; pick "digest".
- `View source` appears twice and opens "Show raw YAML". Three disclosure looks on one page.
- Editor: previewing unchanged text shows "No text changed." and still offers `Approve and merge with passkey`. Hide the button when there is no change.
- Editor errors leak Go types: "field foo not found in type policy3.File". Proposed: "Line 4: `foo` is not a policy key." Errors are plain black bullets; the diff has no colour here although the Owner page colours the same diff.
- The YAML carries the comment "Change it with `archfit request`, never by hand." while the page offers `Edit`. Say on the editor who it is for: "Owners can edit here. Each edit needs your passkey and goes through the policy pull request."
- Volatility, subdomain, minimum balance appear with no gloss. One line each on first use is enough.

### 5.4 Passkeys `/r/<owner>/<repo>/passkeys`

For: register and remove the owner's passkeys. Must understand: where they work, what removing the last one means.

- Reachable only from the editor ("Your passkeys") and from Home step 3 when the user has none. Not in the tabs; pumba Home never mentions it. Add a link in the user menu or a tab.
- No way back, and `?return=` changes nothing visible. Show "Back to …" when it is present.
- `Remove` has no accessible name per key and no warning beside it; the consequence of removing the last key is inside a paragraph. Whether a confirmation follows was not tested.
- Keys are listed as `Passkey 1 T41KinrE`. Show something the owner recognises (a name they give it, or the device kind).
- "You have 2 passkeys in this App installation." under a repository URL. Proposed: "Your passkeys work in every repository of this account where the policy names you as owner."
- The 60-word paragraph mixes four rules. Put each rule beside the control it concerns.

For: the check status and who does what next. Must understand: the status, why, and "what do I do".

- Records are unboxed lines here and a monospace box on the Request page. One record block.

### 5.7 Owner pages `/r/<owner>/<repo>/owner/…`

For: the owner approves the first policy or a workflow change, confirms or reverts a policy changed outside the flow. Must understand: exactly which files, and that approval is not a pass.

## 9. Decisions that are yours

Everything else above was decided by "simple, reliable, expected". These three change the design document or the contract, so they need you. Recommended first.

1. **The word "review".** It is Not-used in the design, aimed at the report, but the matcher bans it everywhere, so about 15 phrases are exempt.
   - A (recommended): amend the design to ban it only as a name for the report; delete every exemption list. Example stays: "Review workflow change".
   - B: keep the ban; reword. Example becomes: "Read and approve the workflow change".
2. **Name of the policy-change pull request.** The design says "architecture pull request"; the UI and guide say "policy pull request"; M3 says "proposal".
   - A (recommended): "policy pull request" everywhere, and edit the design.
   - B: "architecture pull request" everywhere, and edit the UI and guide.
3. **The operator's verb.**
   - A (recommended): "admit" / "admitted" for installations; "approve" stays the owner's word. Example: "Accounts admitted to this App".
   - B: keep "approve" for both.
