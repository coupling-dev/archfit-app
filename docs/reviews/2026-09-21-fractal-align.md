# Alignment review — design tree versus code

Date: 21 September 2026. Branch `implement-archfit-app`. Scope: all 29 modules under
`internal/` plus `cmd/reporter`. Method: a scripted pass (exported surface against each
Public Contract, direct imports against each Integrations section, test names against
each Test Specification) and four read-only semantic reviews (wire and store, github,
gate, control with app and root). Neither side is assumed right.

Result: 1 Critical, 12 Significant, about 34 Minor. The trust invariants hold in code:
the gate's dependency closure is `wire`, `github`, `store` and itself; nothing trusted is
read from the head tree except to hash an owner-approved candidate; `neutral` exists only
for `archfit/state`; every error path ends in 503 with nothing published; the Store is
only read. Exported surfaces match every Public Contract; every direct import is
documented; every named test exists; no module is unimplemented; `cmd/reporter` is 31
lines and holds no logic.

Resolution column: **code** = the design is right, change the code; **doc** = the code is
right, update the module.md; **accept** = record the divergence in the design.

## Pattern

Eight of the twelve Significant findings are one thing: a rule owned by one module and
written again in a neighbour, because each module was implemented in isolation from its
own spec and the specs restated rules as prose rather than publishing them as a function
in the owner's contract. The fix has the same shape each time: the owner exports the
predicate, the neighbours call it, and the restated prose becomes a marked contract block.
