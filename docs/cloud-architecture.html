01 /

Не собирать environment вручную

Рекомендация: использовать уже подготовленный OpenTofu-код. Это Terraform-compatible IaC. Не нужен второй набор ресурсов, созданный командами в Console или через gcloud.

ОСНОВНОЙ ИНСТРУМЕНТ

OpenTofu / Terraform

Создаёт Firestore, secrets без значений, service accounts, IAM, registry, Cloud Run, queues, Scheduler и monitoring.

Два stack: infra/data и infra/runtime. Изменения проходят PR → plan → owner approval → apply с workstation.

ОГРАНИЧЕННЫЙ BOOTSTRAP

Owner + gcloud / Console

Login, проверка project и guardrails, создание state bucket, регистрация GitHub App, secret values, domain verification и DNS.

Secret values не должны попадать в Terraform variables, state, git или HTML. DNS и billing budget остаются у owner.

ПОСЛЕ СОЗДАНИЯ INFRASTRUCTURE

GitHub Actions

Собирает App image, публикует его в Artifact Registry, выпускает revisions и переключает traffic.

CI не делает Terraform apply. Image и traffic исключены из Terraform drift через ignore_changes.

Почему Google Cloud здесь подходит: уже написаны Cloud Run, Firestore и Cloud Tasks adapters. Для beta это managed services без VM и Kubernetes. Scale-to-zero уменьшает idle compute, но не гарантирует нулевой счёт: остаются storage, registry, backups, logs и traffic.

Основание: infra runbook, runtime settings, deploy workflow.

02 /

Где установлены компоненты

Два App process используют один Go binary и один image. Разделение по ролям, а не два разных продукта. Engine image — другой: он запускается на GitHub runner, не на Cloud Run.

1Browser → public: HTTPS, OAuth login и session cookie.

2GitHub → public: webhook с HMAC signature.

3CI → public: JSON report + GitHub OIDC token.

4Public → Tasks: verified webhook; не report upload.

5Tasks → worker: Google ID token от archfit-invoker.

Обратная связь: public и worker вызывают GitHub API через installation token.

RUNTIME SHARED SERVICES

Secret Manager

Секреты монтируются файлами в revisions. Отдельные runtime service accounts и pinned secret versions.

OPERATIONS

Logging + Monitoring

Logs, uptime, alerts о 5xx, очередях, sweep и guardrail changes. Полнота telemetry отдельно отмечена в checklist.

RELEASE, НЕ ANALYSIS

Artifact Registry + GCS

Registry хранит App images. GCS bucket хранит Terraform state двух stack. Ни один не является хранилищем customer reports.

Сеть остаётся простой. В текущих infra/ нет отдельной VPC, subnet, NAT, load balancer или Cloud Armor. Internal ingress worker — настройка Cloud Run, а не «частная VM». HTTPS/TLS на публичном domain обслуживает Cloud Run domain mapping с managed certificate. Исходящие HTTPS-запросы к GitHub и Google APIs не ограничены отдельным egress allowlist.

Основание: Cloud Run settings, queues и Scheduler, role routes.

03 /

Как это работает как GitHub App

REPO 1 · ANALYZER

archfit

CLI и engine image в GHCR. Собирает факты и выпускает architecture-state report. Не получает App private key или cloud credentials.

REPO 2 · EXECUTION ADAPTER

archfit-action

Composite Action на customer runner. Action закреплена commit SHA, engine — per-platform image digest. Загружает результат после завершения container.

REPO 3 · CONTROL & FEEDBACK

archfit-app

Cloud Run runtime. Проверяет provenance и approved inputs, обслуживает UI, создаёт checks, comments и reviewable PRs.

Один обычный pull request

  1. GitHub запускает две независимые линии

    Webhook приходит в public intake → queue → worker. Параллельно customer workflow запускает Action. Worker сам не анализирует исходники.

  2. Action готовит trusted inputs

    Policy, baseline и labels берутся из git blobs. Для PR изменённый файл может браться с head; App примет его только с owner approval на точный head SHA. Иначе доверяет base ref.

  3. Engine выполняет check в CI

    Container получает inputs read-only, но рабочее дерево остаётся writable. GitHub upload token создаётся после выхода container и не передаётся ему.

  4. Action отправляет результат в public App

    POST /v1/reports: report, envelope с identities/digests и короткоживущий GitHub Actions OIDC token.

  5. App сверяет, а не верит envelope

    OIDC signature и audience, workflow/run/commit через GitHub API, image manifest, approved policy, baseline/labels и owner approval.

  6. GitHub получает feedback

    archfit/state, обновляемый comment и, в required mode, archfit/gate. Upload обрабатывается синхронно на public service, не через Tasks.

Что является источником истины

  • GitHub protected ref: .archfit.yaml, .archfit-app.yaml, baseline, labels, approved workflow.
  • GitHub API: фактические repository, installation, PR, commits, reviews и workflow run.
  • App release manifest: разрешённые engine image digests, platform и measurement profile.
  • Firestore: grants/entitlements, consent, LLM budget и краткоживущие publication leases. Не копия repository и не report history.

OIDC ≠ независимая проверка анализа. Он удостоверяет отправителя и claims. Измерение остаётся customer-attested: target-controlled code в CI может влиять на результат. Нельзя называть весь report «verified».

Report содержит metadata: пути, module names, line numbers, metrics и findings. Это не «нулевая утечка информации». No-source schema запрещает snippets, tool logs и raw model output.

Fork PR: текущая связка не даёт ему enforceable gate. Action сохраняет artifact без upload, App показывает fork_unsupported. Нельзя включать привилегированный pull_request_target как обход.

Четыре слоя защиты worker

  1. Internal ingress, без прямого internet access.
  2. Invoker IAM: разрешён archfit-invoker.
  3. Queue-level target override: webhook task нельзя направить на grants.
  4. Grants требуют дополнительный operator token.

Internal ingress ограничивает источники, а IAM — identity. Один контроль не заменяет другой. CI проверяет exposure и queue routing после release.

Граница доверия остаётся видимой

Оба runtime SA имеют доступ ко всему Firestore state. Между tenants нет отдельного IAM perimeter. Компрометация public runtime — серьёзный риск, даже если operator token ему недоступен.

Deploy SA не получает право менять IAM, но может менять service configuration и запускать код от runtime SA. Это привилегированная identity, не «безопасный uploader».

Cloud Tasks не пишет audit log для CreateTask. Нельзя обещать полный audit создателя grant task. Доступ owner к operator queue должен оставаться ограниченным.

Основание: routes и queue-only intake, queue IAM / routing, service accounts, permitted LLM context.

Какие secrets существуют и кто их получает

Secret Manager хранит значения. Cloud Run монтирует pinned versions файлами; env содержит *_FILE path, не сам secret. Таблица показывает текущую IaC-конфигурацию: worker получает только App key, webhook secret и operator token. Live IAM и serving revisions отдельно не проверены.

Имена secret ресурсов не являются секретными значениями. Значения при подготовке документа не читались.

Долгоживущие secrets и временные tokens

Храним: App private key, webhook/OAuth secrets, cookie key, operator token, optional Anthropic key.

Получаем на время: installation tokens, GitHub upload OIDC, Google access/ID tokens. В IaC не создаются Google service-account JSON keys.

GitHub App ID, OAuth client ID, project ID и image digest — configuration, не secret values.

Rotation и rollback связаны

Новая secret version попадает в runtime только с новой revision. Старую оставляют включённой, пока rollback может вернуть revision, которая её использует.

При compromise старую version отзывают сразу; rollback выполняют старым image с текущими secrets. Для overlap Terraform монтирует webhook_secret_previous_version вторым файлом того же secret на обоих service. По умолчанию previous version не монтируется.

Secret access ограничен в IaC: OAuth secret и cookie key доступны только public role. Это не подтверждает изменение live IAM до reviewed apply и обновления worker revision. App private key всё ещё попадает в process memory; KMS signing — отдельное будущее усиление, не реализованная защита.

Основание: secret IAM map, mounts, role-specific loading, rotation design.

Как создавать и выпускать environment

Разделены два контура: lifecycle инфраструктуры и выпуск application image. Это не deploy customer engine: он остаётся в customer CI.

Infrastructure lane · Owner workstation

1. PR + OpenTofu plan

Identity/project/region, проверки IaC, live inventory, import существующих guardrails. Plan сохраняется, изменения и replacements просматривает owner.

→
2. Два независимых state

data: Firestore, IAM, secrets, registry, WIF.
runtime: services, queues, Scheduler, domain, alerts.

→
3. Approved plan → apply

GCS remote state: coupling-dev-510710-tfstate, prefixes data / runtime. Runtime читает outputs data stack.

Application release lane · GitHub Actions

1. main → OIDC → Google WIF

Provider привязан к numeric repository ID, refs/heads/main и конкретному deploy.yaml. Затем identity archfit-deploy.

→
2. Build once → image digest

App image публикуется в региональный Artifact Registry. Worker и public получают новые revisions без переключения traffic.

→
3. Canary → promote → checks

Public canary проходит /ready. Затем worker → public promotion. Post-release checks проверяют worker exposure и queue targets.

Что уже подготовлено в репозиториях

  • infra/data, infra/runtime, provider lock files и mock tests.
  • Firestore и Cloud Tasks adapters; role routes и Google identity checks.
  • .github/workflows/deploy.yaml, release/check/rollback scripts и tests.
  • App понимает engine v3, Action поддерживает discovery, baseline и reanchor.
  • First-deployment runbook, security и operations docs.

Что эти проверки не доказывают

/health — process alive. /ready — App key работает с GitHub и Store отвечает. Ни одна проверка не доказывает end-to-end GitHub installation, queue delivery и PR gate.

Public canary до promotion не получает реальных uploads/webhooks. Post-release check запускается уже после переключения traffic; при failure нужен явный выбор rollback, не обещание автоматического восстановления.

Rollback scripts поддерживают traffic rollback и повторный release прежнего image. Смена формата Firestore state должна оставаться совместимой с предыдущей revision.

Основание: first deployment, WIF restriction, release order, post-release checks.

07 /

Порядок первого запуска

Это план действий, не список уже выполненных операций. Не запускать все команды подряд: каждый apply/deploy требует проверки destination и согласования конкретного plan или image.

  1. Сверить identity, cloud inventory и guardrails

    Owner account с 2-step verification. Проверить project/region, billing budget, enabled APIs и quotas. Создать или проверить versioned GCS state bucket. Не дублировать существующие ресурсы.

  2. Создать data stack по reviewed plan

    Импортировать подготовленные guardrails. Создать Firestore, IAM, Secret Manager containers, Artifact Registry и WIF. Secret values в plan не добавлять. Firestore location выбирается один раз.

  3. Подтвердить домен и зарегистрировать GitHub App

    Homepage: https://app.coupling.dev. Callback: /auth/callback. Webhook: /webhooks/github, пока inactive. Установку на repos пока не включать.

  4. Добавить App IDs и secret values

    App ID и OAuth client ID нужны runtime plan. Secrets добавить в Secret Manager; pin versions. Затем запустить CI в mode: build, получить build.json и задать initial_image_digest. Этот mode не deploy-ит Cloud Run. Anthropic key необязателен.

  5. Создать runtime, DNS и TLS

    Queues/Scheduler остаются paused. Services сразу стартуют с реальным App image из своего Artifact Registry, закреплённым initial_image_digest. Hello/placeholder image больше нет. Не активировать webhook до проверки runtime и release pipeline.

  6. Проверить первый runtime и release pipeline

    Manual deploy.yaml на main. Проверить canary, promotion и post-release result. Push releases включать через RELEASE_ON_PUSH только после успешного первого запуска.

  7. Включить processing и пройти один test repository

    Согласованным runtime change снять pause, активировать webhook. Install App → OAuth → setup PR → discovery → policy PR → baseline в pinned CI image → owner review. Сначала advisory mode.

  8. Проверить failure paths, потом required gate

    Boundary violation, missing upload, protected-file approval, reanchor, queue retry и sweep. Перед внешними installations проверить rollback, backup restore, secret rotation и alerts. Затем PR с gate: required, только после него — required check в GitHub ruleset.

Какие права нужны GitHub App при регистрации

По текущему API contract: repository permissions checks: write, pull_requests: write, contents: write, actions: write, workflows: write, metadata: read; organization permission members: read для team owners. Это права самой App, не customer workflow.

Customer workflow использует contents: read и id-token: write, без App private key. App installation сначала ограничить одним test repository. Реальные permissions и OIDC claims подтвердить end-to-end.

Источник: GitHub API integration contract.

Не требовать отсутствующий check. В advisory mode App не публикует archfit/gate. Если заранее добавить его в required checks, merge останется заблокирован. Первую baseline принимают после review; при engine/profile migration используют reanchor, а не молчаливое принятие нового долга.

Видимые ограничения и расхождения

Исправлено в IaC

Worker secrets ограничены

OAuth secret и cookie key исключены из worker IAM и mounts. Mock tests проверяют точный набор доступов и отсутствие лишних file references. Live изменения требуют отдельного reviewed apply.

Wired in IaC

Webhook rotation без нового secret

Опциональный webhook_secret_previous_version монтирует старую pinned version рядом с current на обоих service. Overlap включается только на время rotation; нужен отдельный reviewed apply и release.

Wired in IaC

Request trace configuration

GOOGLE_CLOUD_PROJECT задан для обоих service, чтобы request traces связывались с Cloud Logging. Live correlation и alerts ещё нужно проверить после deployment.

Design limit

Нет managed discovery и sandbox

Onboarding предлагает только Customer mode. Отдельный sandbox driver не написан, backend продолжает отказывать без него. Managed AI assist и его consent checks сохранены.

Beta trade-off

Без WAF, staging и organization

Эти компоненты не следует рисовать как существующие. Design предусматривает отдельные triggers для staging, Cloud Armor и organization перед расширением.

Capacity limit

0–2 instances на service

По 1 vCPU и 512 MiB. Четыре instance заполняют текущую 4-vCPU quota; rollout может ждать capacity. Scale cap и budget alerts — не жёсткий денежный stop.

Точные команды: infra/README.md. Launch drills: operations → Before launch. Новые infrastructure changes этим документом не применяются.
