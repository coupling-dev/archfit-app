Design notes · Charter

  
Who it suits
Architecture owners and governance: teams that must agree on an architecture, keep a record of changes, and explain decisions to others. Long-lived and regulated systems.

  
Core bet
The product is the agreement. If the intended architecture reads like a short, numbered document that people sign off, then every finding, exception, and PR can refer to a clause, and review becomes a conversation about the agreement.

  
What gets easy
  • Defining the architecture with owners, clause by clause.
  • Explaining a blocked PR: “breaks §3.1”.
  • Auditing exceptions and their end dates.
  • Scaling past 50 modules with the matrix.

  
What gets hard
  • Less instant visual intuition than a map.
  • The charter can read like documentation and be opened rarely.
  • Sentence templates must cover every rule type the engine adds.

  
Data it needs
EXISTS TODAY Policy, settings, labels, baseline on main. Compliance and seams from the latest default-branch report artifact, which GitHub keeps for a limited time. Checks and comments on PRs.
NEW Sentence templates per rule type (UI only). Typed amendment forms. Amendment history from merged PRs via the GitHub API, no storage.

  
Build cost
Medium. control/ui: charter rendering, matrix as server-rendered HTML, amendment forms that write YAML diffs. gate/feedback: clause references and collapsed sections in the comment. No engine change.

  
Risks and mitigations
  • Text drifts from meaning → text is generated from the policy, never written twice.
  • Nobody opens it → compliance chips and the PR comment link back to clauses.
  • Matrix is unfamiliar → legend, direct counts in cells, and a “what it shows now” list.
